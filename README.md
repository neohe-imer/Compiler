# MiniLang

A small C++20 language implementation with two execution backends: a tree-walking interpreter and a bytecode compiler with a stack-based virtual machine. It is an educational project for exploring how source code becomes executable instructions.

```text
Source → Lexer → Tokens → Parser → AST ─┬─→ Interpreter → Output
                                       └─→ Compiler → Bytecode → VM → Output
```

## Quick start

Requirements: a C++20 compiler, CMake 3.16 or newer, and a build tool such as Make, Ninja, or Visual Studio. There are no third-party runtime or test dependencies.

From the repository root:

```sh
git clone https://github.com/neohe-imer/Compiler.git
cd Compiler
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --config Debug --parallel
ctest --test-dir build -C Debug --output-on-failure
```

Run the included program through either backend:

```sh
./build/minilang --mode=interp Compiler/minilang/examples.ml
./build/minilang --mode=vm Compiler/minilang/examples.ml
```

With Visual Studio or another multi-configuration generator, the executable is under `build/Debug/` (on Windows, `build/Debug/minilang.exe`). Both commands print:

```text
0.000000
1.000000
2.000000
3.000000
4.000000
123.000000
```

You can also configure the language subdirectory directly with `cmake -S Compiler/minilang -B build` in a fresh build directory.

## Write a program

Save this as `count.ml`:

```text
// Variables, loops, arithmetic, and branching.
let x = 0;
while (x < 5) {
  print x;
  x = x + 1;
}

if (x == 5) {
  print 123;
} else {
  print 999;
}

// Logical operators short-circuit in both backends.
print true || undefined_name; // true: the right side is never evaluated
```

```sh
./build/minilang count.ml          # interpreter is the default
./build/minilang --mode=vm count.ml
./build/minilang --help
```

The VM compiles and executes in memory; it does not produce native machine code or a bytecode file. Exit codes are `0` for success, `1` for file/language/runtime errors, and `2` for invalid command-line usage.

## Language reference

| Feature | Syntax / behavior |
| --- | --- |
| Values | Double-precision numbers and `true` / `false` |
| Number literals | Integers and decimals, such as `42` and `3.14`; unary `-` handles negatives |
| Declaration | `let x = 10;` or `let x;` (defaults to zero) |
| Assignment | `x = 20;`; assignments are expressions and return the assigned value |
| Output | `print expression;`; numbers print with six decimal places |
| Branches | `if (condition) statement` with optional `else statement` |
| Loops | `while (condition) statement` |
| Blocks | `{ statement; ... }` groups statements |
| Comments | `//` through the end of the line |

Arithmetic (`+`, `-`, `*`, `/`), comparisons (`<`, `<=`, `>`, `>=`), and equality (`==`, `!=`) require numeric operands. Boolean equality is currently unsupported. Conditions accept booleans and numbers: zero is false, nonzero is true. `!`, `&&`, and `||` return booleans. Both logical operators evaluate the right operand only when needed.

Precedence, from lowest to highest:

1. Assignment: `=` (right-associative)
2. Logical OR: `||`
3. Logical AND: `&&`
4. Equality: `==`, `!=`
5. Comparison: `<`, `<=`, `>`, `>=`
6. Addition/subtraction: `+`, `-`
7. Multiplication/division: `*`, `/`
8. Unary: `!`, `-`
9. Literals, variable references, and parenthesized expressions

Binary operators at the same precedence are left-associative. Expression statements, declarations, and `print` statements end with a semicolon.

### Current boundaries

- Variables share one global environment. Blocks do not create lexical scopes; redeclarations replace a value, and assignment can introduce a name. Reading an undefined name is an error.
- No strings, functions, arrays, modules, `for`, `break`, or `continue`.
- Numeric literals do not support exponent notation. Division uses the host's floating-point behavior, with no explicit divide-by-zero diagnostic.
- The compiler uses 16-bit constant/name indices (up to 65,536 entries each) and signed 16-bit relative jumps (−32,768 through 32,767 bytes). It reports overflow instead of silently truncating operands. Total code size can exceed 64 KiB if individual jumps fit.
- Lexer/parser errors include line numbers; runtime and compiler errors do not yet carry source locations.
- The VM checks operand reads, pool indices, stack underflow, opcodes, and taken jump bounds. It is intended for compiler-generated bytecode, not as a sandbox or a complete verifier for untrusted bytecode. Execution and parser recursion have no resource limits.

## Code map

All language sources are in [`Compiler/minilang/src`](Compiler/minilang/src). Implementation files use the `.c++` extension.

| Files | Responsibility |
| --- | --- |
| `token.h`, `lexer.h`, `lexer.c++` | Token definitions, keywords, scanning, and line tracking |
| `ast.h`, `parser.h`, `parser.c++` | Owned AST nodes and recursive-descent parsing |
| `value.h` | Number/boolean values, conversions, and formatting |
| `interpreter.h`, `interpreter.c++` | Direct AST execution |
| `bytecode.h`, `compiler.h`, `compiler.c++` | Instructions, constant/name pools, control-flow lowering |
| `vm.h`, `vm.c++` | Stack execution and runtime checks |
| `main.c++` | Command-line parsing, file loading, and backend selection |

`minilang_core` is the shared CMake library target used by the CLI and tests. There is one compiler and one VM implementation. Logical expressions lower to conditional branches; `if` and `while` share checked jump patching.

## Development and tests

```sh
cmake --build build --config Debug --parallel
ctest --test-dir build -C Debug --output-on-failure
```

The regression suite compares both backends with explicit expected results for expressions, assignments, branches, nested loops, and short-circuit side effects. It also checks error cases, large code offsets, constant limits, compiler/VM reuse, malformed bytecode, CLI exit codes, and the example program. GitHub Actions is configured to build and test on Linux, macOS, and Windows.

For Clang/GCC sanitizer checks:

```sh
cmake -S . -B build-sanitize -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_CXX_FLAGS="-fsanitize=address,undefined -fno-omit-frame-pointer" \
  -DCMAKE_EXE_LINKER_FLAGS="-fsanitize=address,undefined"
cmake --build build-sanitize --parallel
ctest --test-dir build-sanitize --output-on-failure
```

When adding a language feature, update both backends and add tests with expected output and failure behavior. Useful next steps include source spans throughout the AST/bytecode, lexical scopes, and a bytecode disassembler.
